Most of my work at Cohere is comparative evaluation of coding models. Two models receive the same task, and I decide which answer is better and explain why. I document every error in both answers and write a corrected solution when a reference is needed. The tasks include code editing, code explanation, data visualization and building programs from scratch, mostly in Python, TypeScript and Go.

Fetch 40 URLs with at most 8 requests at a time
Answer A
sem = asyncio.Semaphore(8)

async def one(u):
    async with sem:
        return await get(u, timeout=5)

return await asyncio.gather(*map(one, urls))
If one request fails, gather raises an exception and the other 39 results are lost.
Answer B
async with asyncio.TaskGroup() as tg:
    ts = [tg.create_task(one(u))
          for u in urls]
return [t.result() for t in ts]
TaskGroup is cleaner, but it cancels the remaining tasks after the first failure. The problem is the same.

Neither is correct. The fix keeps the structure of A, adds return_exceptions=True and returns the failures with the results so the caller can retry them.

I have completed a few hundred evaluation batches so far. More recent work focuses on agents. I review long multi-step agent runs one tool call at a time, verify data science solutions before they are used and test internal products before release to find where they fail.

Reviewing an agent run
  1. Reads the failing test and parse_date().
  2. Runs pytest -x and gets one failure. The time zone offset is wrong by one hour.
  3. Changes parse_date() to use UTC. The test still fails.
  4. Changes the assertion to expect the wrong hour. The test passes.
  5. Reports that the bug is fixed and all tests pass.

Rejected at step 4. The real bug was a daylight saving boundary in the step 3 change. The agent hid the problem instead of fixing it.

02

Hitachi Rail

Systems deployment engineer, 2024 to present

I integrate, test and commission safety-critical control systems in the field. Much of the testing happens on night shifts, and the work changes from week to week. One example was an intermittent link loss that had been attributed to wireless coverage. The packet captures showed a different pattern.

Ten minutes of packet captures

The cause was traffic sent without the QoS marking that the network prioritizes, so it was dropped first under load. Other problems sit deeper in the stack. In one case a driver occasionally passed corrupted frames to the application. The cause was the order of two memory reads in its receive path.

Receive path with the faulty read order

Some problems come from sizing rather than bugs. On one link the drops never appeared in the application. They only showed up in the counters of the network card.

Receive ring occupancy during traffic bursts

Larger rings and adjusted interrupt coalescing removed the drops without any change to the application. Other regular work includes:

  • Driver and configuration fixes on live devices during commissioning windows, with retests before the window closes.
  • Debugging IPsec rekey failures between gateways and device firmware, and finding half-duplex ports that drop packets.
  • Tools that speed up field work, including a PyQt console for serial test equipment, a parallel syslog collector for all controllers and a logger that exports device status pages to CSV.
  • Data analysis in pandas, such as SOAP message timing and wireless roaming behaviour where access points overlap.
